Supplementary check (run after the main benchmark, 2026-10-15).
Question: is Java's jump at n = 1600 (6.5 times C) caused by the fixed run order of the main
benchmark? There, C ran all its sizes first (including 600 s at n = 3200), so Java at n = 1600
started on a laptop that had been under full load for about 10 minutes, while C at n = 1600
had run after only a few seconds of load.

Setup: n = 1600, same inputs, binaries and settings as the main benchmark (pinned to logical
CPUs 0-11, high priority, C 1 warm-up, Java 2 warm-ups). Four processes in the order
Java, C, C, Java, each started after a 60 s idle pause (cool-down).
C: 3 measured runs per process; Java: 2 measured runs per process.

Medians per process: Java 26.9 s and 25.3 s; C 3.02 s and 3.02 s.
Java / C = 8.4 to 8.9 (main benchmark: 26.79 / 4.122 = 6.5).

Observation: with alternating processes and cool-down pauses Java still takes about 8.5 times
as long as C at n = 1600, so the jump is not caused by the run order or by the laptop heating
up. The main benchmark's ratio (6.5) is the more conservative value; C at n = 1600 was faster
here (3.0 s instead of 4.1 s).
